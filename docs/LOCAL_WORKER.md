# Fold Studio local development worker

This is a separate user-level macOS service, not another Fold Studio app. It does not replace the current app, restart experiments, merge patches, or require a cloud model. Its source is `local_worker/`; control it with `scripts/fold-worker` from this repository.

## Dispatch and retrieve

```sh
scripts/fold-worker start
scripts/fold-worker submit scripts/worker-examples/config-check.json
# Return later; no active Work turn is needed while the service executes.
scripts/fold-worker jobs
scripts/fold-worker report TASK_ID
scripts/fold-worker inspect TASK_ID
scripts/fold-worker logs TASK_ID
scripts/fold-worker health
```

A single `submit` accepts a complete JSON task and wakes the independent service through a private FIFO. SQLite WAL stores tasks, atomic claims, timestamps, heartbeats, events and results. Full logs and `report.json` remain local; `summary.json` is intended for a later Work review. It reports actual command exit codes, changes, errors, resource observations, revision and artifact paths. Prose acceptance criteria remain review items; the worker does not claim scientific correctness merely because a test exits zero.

## Controls

```sh
scripts/fold-worker cancel TASK_ID
scripts/fold-worker emergency-stop
scripts/fold-worker clear-emergency
scripts/fold-worker resume BLOCKED_TASK_ID
scripts/fold-worker rollback FINISHED_TASK_ID
scripts/fold-worker stop
scripts/fold-worker disable
scripts/fold-worker enable
scripts/fold-worker notifications on
scripts/fold-worker notifications off
scripts/fold-worker benchmark
```

Stop/disable affect only this development service and its owned children. Emergency stop pauses queued work and stops owned execution; it never signals the molecular app or unrelated scientific processes. Rollback preserves a patch before removing an owned review worktree; it refuses untracked files. There is no automatic merge/apply-to-active-checkout command. Never update worker source while a task is running; stop this service, update and test, then start it again. Reloading this worker does not require rebuilding Fold Studio.

State is stored in `~/Library/Application Support/FoldStudioWorker`, mode 0700. The launch agent is `~/Library/LaunchAgents/org.foldstudio.development-worker.plist`. Notifications are best-effort macOS requests; delivery depends on notification settings. Notification outcomes never determine scientific or task success.

## Task capabilities

Schema 1 requires a type, instructions, exact authorized edit paths, acceptance criteria and named operations. IDs are generated by the broker. Defaults and maximums are checked at submission; unknown fields and arbitrary command strings are rejected. See the runnable examples in `scripts/worker-examples/`.

- `deterministic`: no edit capability; runs only approved operations.
- `patch`: exact before/after replacements with original SHA-256 checks, in a detached worktree. Optional explicit repair batches run only after a failed check.
- `local-ai`: installed local Aider and Ollama, exact existing edit files, isolated worktree, bounded inference and deterministic acceptance. Scientific/security-sensitive paths escalate instead.
- `reasoning`: records a blocked Tier 3 escalation without invoking any model.

`operations` lists the supported names. These include configuration checks, Git whitespace checks, TypeScript checking, frontend/backend tests, worker tests and peptide tests. The catalogue is trusted source code, not generated shell text. Installed dependencies or fixtures may still be absent; such failures are reported rather than downloading dependencies or relaxing the sandbox. The build available here is TypeScript compilation/checking; automatic native packaging/installation is deliberately not a task capability. Use the existing guarded `scripts/build-local-app.sh` workflow for an approved app update.

Each edit task may authorize at most eight exact existing files. Symlinks, traversal, `.git`, `.env*`, `private`, dependency directories and `AGENTS.md` edits are refused. Changed paths, sizes and diffs are audited. Patches stay review-only. An active dirty checkout blocks editing tasks rather than risking unfinished work. At most three retained edit worktrees may exist per broker; review/rollback them before creating more. No history rewrite, push, dependency install or destructive shell command can be submitted.

Limits: one executing broker task; 1–3600 seconds per task; at most two correction retries; at most eight named checks per attempt; 1 MiB review patch/file limits; bounded log sizes and a 128 MiB per-task artifact ceiling. The wall timeout, log and sampled RSS watchers stop only owned development children. Large persistent dependencies/models are outside per-task staging and are not copied for every job.

## Crash handling

An exclusive daemon lock prevents duplicate services. Claims use `BEGIN IMMEDIATE`. The runner heartbeat is updated during execution; service heartbeat is updated while idle. Owned runner watchdogs terminate their own process group if their daemon parent disappears. On daemon restart, interrupted tasks become `blocked`; no possibly completed side effect is replayed automatically. Inspect the retained logs/patch and explicitly resume or submit a corrected task. Resume refuses while the recorded runner identity still exists. This is conservative recovery, not a claim of exactly-once arbitrary external side effects.

## Memory and scientific priority

Admission reads macOS pressure and estimates reclaimable pages, scans known scientific workers and consults the existing research job database read-only. Unknown/abnormal pressure, active saved jobs or demanding related processes block development. Default headroom is 4 GiB plus the declared task budget. A workload appearing during execution causes the worker to yield. Scientific worker detection is conservative and cannot identify every future external program; register new scientific runner patterns when adding engines.

The model server exists only during a local-AI task, uses one loaded model and one request at a time, and is terminated/unloaded afterward. It has lower CPU priority. Command process-tree RSS is sampled; GPU/unified-memory allocation is additionally constrained by model choice, context/output bounds and macOS pressure. This is a soft governor, not a kernel-enforced Metal memory quota; sample peaks may underestimate brief spikes. Never raise budgets simply to force a job past pressure checks.

## Local AI installation and boundaries

The user explicitly approved installing Aider/Ollama and one small coding model. Installed versions and model identity are recorded in the validation report. Aider has its own environment under the worker state directory; no Fold Studio scientific runtime was modified. The one model store is the worker's `models/` directory. The initial qualified model is `qwen2.5-coder:3b` (Q4_K_M, about 1.9 GB), selected to keep memory modest rather than to claim frontier coding ability.

```sh
scripts/fold-worker configure-local-ai \
  --aider "$HOME/Library/Application Support/FoldStudioWorker/runtime/aider/bin/aider" \
  --ollama /opt/homebrew/bin/ollama
```

The worker starts an **owned** Ollama server with `OLLAMA_NO_CLOUD=1` inside a macOS sandbox allowing loopback networking only. It does not reuse an unknown existing server. A separate metered loopback gateway permits only the selected installed model, limited metadata routes and chat inference. It rejects redirects, unapproved endpoints, excess context bytes and model calls. There is no automatic model pull. Chat requests force non-streaming, 8192 context tokens, at most 1200 generated tokens and unload-on-completion. Task limits permit at most three inference requests across retries. Aider's provider, weak model and edit format are explicit; auto-commits, tests, linting, shell suggestions, URL detection, analytics, notifications and update/release-note checks are disabled. Tests run through the deterministic executor afterward.

Both model and agent use sanitized environments without inherited API keys or SSH agent credentials. Seatbelt restricts filesystem access to source/dependencies/task artifacts and denies personal home files, secrets, external networking and unauthorized writes. System libraries remain readable. This is defense in depth for explicitly authorized development, not isolation from malicious software already running as the same macOS user. Neither installed Codex CLI nor a command running locally implies local inference; this adapter uses the actual installed GGUF model through Ollama. Paid/cloud adapters are absent.

A small local model has a narrow capability envelope. Failed coding attempts stop at the specified budget and leave diagnostics for Work. Do not route numerical-method design, scientific interpretation, security changes or major architecture to it. Local AI success on a fixture is not general scientific coding qualification.

## Work notifications and honest savings measurements

There is no automatic callback into this Work chat. The supported interface used here is local task submission and explicit later report retrieval. Official Codex App Server APIs can start Codex turns, but doing so would require a separately configured authorized adapter and may consume allowance; it is not a free local inference channel. OpenAI API webhooks describe API events, not an arbitrary worker-to-this-chat wake mechanism. No recurring cloud reasoning or heartbeat automation is installed.

Use prospective matched tasks to measure savings: same revision, objective, checks and machine conditions; compare direct Work execution with one worker dispatch and later compact review, alternate order and repeat. Record pass rate, wall time, local peak memory, Work interventions/tool calls and observable account-window snapshots with concurrent-usage caveats. The available account percentages are shared and coarse, not per-task attribution. Do not convert API tokens, local model tokens, tool-call counts or account percentage movement into an invented Work allowance percentage. The 60–85% and 90% targets remain unverified hypotheses.

The benchmark distinguishes deterministic edits from genuine model-generated edits, deliberately failed checks from successful checks, simulated contention from real scientific runs, and expected escalation from successful implementation. It retains failed attempts and their diagnostics rather than replacing them with a success story.
